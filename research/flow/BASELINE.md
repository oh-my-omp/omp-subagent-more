# 流程编排基线

compact 之后先读这一份，再动手。这里只有必须做到的事和它的理由（理由用用户原话）；不写做法，不写进度。进度在 todo 里。

实现位置：`extensions/flow/`（随 omp-subagent-more 插件加载），eval 辅助 `skills/omp-subagent-more/flow.js`，角色 `agents/flow-*.md`，测试 `tests/flow-store.test.ts`。

## 它为什么存在

- &#32;**一套workflow原语，以一个普通的目标做案例验证编排原语的实际可行性** 
- subagent的控制反转，把主agent从无尽的调度和传话中解放
- 确定性的交接和状态机判断，减少模型因为判断跑偏
- 减少确定性事件需要模型来回传话和判断，平白无故消耗token和推理时间
- 工作流的目的不是langraph式的一下子所有内容跑通，而是在确定性编排的部分尝试去编排，不确定的部分llm退回普通方式，提供最大的灵活性。
- 目的是“低成本模型处理所有这些issue的一个详细编排方案”（omp-config 的 issue 树 320/321/322）：中等及以下难度的工作全部拆给 free、low、mid 模型。流程工具是手段，交付物是那份编排方案；工具做出来以后要拿真实的 issue 试跑，用观察到的模型行为决定怎么组合。“你可以试着跑一个issue并观察这些模型的行为来在编排上选择如何组合”。
- 它属于 subagent more：“为了subagent more去定制增强eval…eval就有了实际上可用的经验”，“把之前设计的东西挪过来，因为这是subagent more的一部分”。

## 怎么拆、谁来做

- 不把整条流程、也不把过大的一段交给一个子代理；issue 本身可以动态拆分；一个代理交回的值可以展开成后面的多项任务。“严禁把所有流程给一个subagent，甚至一个过大的流程给一个subagent，乃至issue本身都可以动态拆分…返回值可能可以用于flatmap”。
- 流程是循环，子代理可以中途退出来求助；通讯只走结构化交回值和按工作单元隔离的白板文件。“workflow必须设计成loop，允许内部的subagent逃生后求助，通讯使用结构化yield和隔离白板文件”。
- 高档模型只做裁决和答复求助，不做实现。“task high的回退仅用于裁决和解决低级模型的求助”。
- 用本项目自己定制的 agent（自己的 system prompt），模型沿用各档已有的模型设置。“在本项目额外定制agent，而不适用系统中的task预定义的system prompt，我只需要你使用对应的模型设置…优化是必须做的”。可以在编排里额外注入规则。
- 模型强弱自己评测，不信描述（“那是瞎写的”）；麻烦的模型可以只做边缘事务或不用；swe2 并发限流很严，要限并发；carbon 已禁用。
- issue 写得细，所以门禁要多，交接用结构化返回值；最终测试不重复验证。“issue本身非常详细所以你实际上可以引入非常多的gate，以及结构化handoff返回值作为交接”。
- 不投票，不做对抗审查循环。正确性靠运行时行为、最终验收和一名意图守护者。“正确性不应该由对抗审查保证，而应该由运行时行为保证”，“并不害怕裁决错误，只要最终验收能通过，并且有意图守护者”。
- 不加沙箱运行。

## 会话

- 不从原会话继续：每次点火都是新会话。交回值必须带交接。后一次会话要能继承前一次会话的工作区，并且可以换模型。“不允许从原始会话继续，但是现在有继承工作空间的实现，然后还需要强制handoff”，“fork自己有继承工作区但是使用不同模型的实现，这值得把东西抄过来”。

## 异常

- 模型抛出的异常是交回 schema 里预先声明的类型，流程里写明由谁接。“这个异常等同于schema有预定义的某种类型，ai运行那样填…workflow里可以写兜底谁处理”。
- 其余失败统一进异常处理：分有名字的和没名字的，默认全部停下；只有被处理过的异常才能接回流程；怎么处理是状态转移是否合法的问题。“其他的异常都统一送给异常处理器，并且分为命名的和不命名的，默认策略是停止所有…怎么处理本质上是状态转移的合法性”。

## 状态

- 一个集中的状态管理器，只追加、不可变；停下、处理、替换、恢复之后状态必须对得上。“需要集中的状态管理器，否则停下来以后，再恢复对不上”，“redux…不可变且本来就不可变”。
- 原语是我们自己提供的，不再包一层；不用 Effect 之类的并发库，内核里也装不了包。
- 声明和代理的生命周期是两回事；调用不阻塞 cell。“声明和agent生命周期不是一回事…我不希望eval阻塞运行放弃repl的好处”。

## REPL

- 定义是可以整个覆盖的对象，改一个盒子不用重写整条流程；不用 diagram 闭包写法。“REPL是一种可以覆盖对象的东西”，“repl最大的优势是可以反悔”，“diagram不利于repl”。
- 状态图和外部状态转移由定义自动得出，不靠手画。
- 原语运行后自己把结果打印出来，不限于 cell 最后一行，也不是回显。“repl的核心是运行后能有正确的结果可以知道”，“不应该是限定在最后一行才被显示”，“回显为什么不是隐式调用print”。
- 不做单独的工具或 eval 环境：外部信息直接拿进来登记为状态，不让模型再抄一遍，中途可以和 gh 之类的调用自由混用。“把外部的信息直接拿进来当作状态注册，而不需要ai再抄一遍，而且中途可以自由混合比如gh这种东西”。
