## 一、为什么旧版 `orchestrate.js` 不够用？

`flow` 之前的 `orchestrate.js` 在真实复杂编排中暴露了 6 个根本性缺陷：

1. **状态在 `eval` 内核内存中**：一旦 cell 被中断或内核重置，正在运行的全部编排进度丢失。
2. **无法动态拆分（无扇出 / `flatMap`）**：只能写死静态 `items: [{ id, stages: [...] }]`，前一个子代理的返回值无法展开成后续的多个子任务。
3. **从原会话继续导致上下文腐化**：`answer(id, text)` 通过 `handle.send()` 把回答发回同一个子代理会话继续，且无法在重做或续接时切换模型。
4. **轮询阻塞 REPL**：`await run.drive()` 在 cell 内用 `sleep(1000)` 轮询 `handle.status()` 并用正则解析 `agent://<id>` 的 Markdown 文本，放弃了 REPL 非阻塞交互的优势。
5. **无法在 REPL 中单点反悔**：定义与运行状态绑死在同一个闭包实例里，改一个阶段就必须整套废弃重来。
6. **无异常分类与门禁回路**：只有 `done` / `needs_input` 两分支 `oneOf`，没有预声明的业务异常路由、没有确定性命令门禁打回重开、也没有统一的运行时异常处理器。

## 二、核心设计基线（不可妥协约束）

以下原则提炼自会话中确立的设计基线，是 `flow` 原语一切机制的依据：

### 1. 会话与工作区：绝不回原会话 + 强制交接 + 继承工作区
- **每次点火都是全新会话**：“不允许从原始会话继续，但是现在有继承工作空间的实现，然后还需要强制 handoff”。
- **强制结构化交接（Handoff）**：无论子代理是正常完成（`done`）还是主动抛出问题（`raise`），其 `yield` 返回值都必须携带 `handoff: { did, decided, unverified }`。没有交接的崩溃会话不允许“接续”，只能从原输入重新点火。
- **跨模型继承工作区**：“fork 自己有继承工作区但是使用不同模型的实现，这值得把东西抄过来”。同一工作单元的后续新会话自动继承上一会话留下的工作区变更（含未提交变更或未合入的任务分支），且可绑定不同模型。
- **隔离白板文件**：“通讯使用结构化 yield 和隔离白板文件”。每个工作单元拥有独立的笔记文件（`flow-boards/<key>.md`），仅该单元的历次会话与答复该单元求助的会话可见。

### 2. 拓扑与拆分：小粒度盒子 + 动态展开 + 业务回路
- **严禁大包大揽与支持动态展开**：“严禁把所有流程给一个 subagent，甚至一个过大的流程给一个 subagent，乃至 issue 本身都可以动态拆分……返回值可能可以用于 flatMap”。
- **流程内建业务回路（Loop）**：“workflow 必须设计成 loop，允许内部的 subagent 逃生后求助”。
  - 子代理遇到未决问题时主动抛出预声明的异常类型（`raises`），流内接线给裁决/答复盒子，答复后原单元以新会话继续。
  - 程序门禁（`checks` 命令盒子）检验不通过时，带着门禁输出将原单元重开（`reopened`）为新会话，**这属于业务编排自身的回路，不属于运行时异常**。

### 3. 异常模型：模型抛出 vs 运行时异常
- **模型主动抛出的异常**：等同于输出 Schema 中预声明的端口类型（`<box>!<type>`），在工作流定义中写明由哪个盒子接手处理（或停在边界等待外部 `answer`）。
- **其余运行时异常**：“其他的异常都统一送给异常处理器，并且分为命名的和不命名的，默认策略是停止所有，如果异常有处理才有可能能接回去，至于说怎么处理本质上是状态转移的合法性”。

### 4. 状态管理：Redux 式不可变单一追加日志
- **集中式状态管理器**：“因为是 repl，所以停下来以后可以处理后并替换。然后也因为是 repl，所以实际上需要集中的状态管理器，否则停下来以后，再恢复对不上”。
- **不可变与纯折叠**：“这个状态管理非常适合 react 社区的状态管理思想，比如 redux，因为确实就应该不可变且本来就不可变，而因为原语是我们自己提供的，所以正常来说不需要任何额外的包装”。
- **只存 Action 序列**：状态完全由会话目录下的 `flow.jsonl` 追加日志折叠（`reduce`）得出；反悔是追加一条 `retracted` / `defined` Action，而不是篡改历史。
- **定义指纹与过期拦截**：每个产出的值记录产生它时的三层指纹（盒子定义 + Agent 定义文件 + 模型绑定设置）。在 REPL 中替换定义后，Store 自动比对出 `stale`（过期）和 `illegal`（非法）项，未显式处理（`keep` 或 `retract`）前拒绝恢复运行。

### 5. REPL 交互表面：纯数据覆盖 + 隐式打印 + 混用外部状态
- **声明与生命周期分离**：“声明和 agent 生命周期不是一回事……我不希望 eval 阻塞运行放弃 repl 的好处”。
- **纯数据对象按名覆盖**：“diagram 不利于 repl”、“REPL 是一种可以覆盖对象的东西”。盒子是纯 JSON 数据，按名字晚绑定引用；改一个盒子只需重新 `define` 那一个盒子，状态图（`wiring`）和合法外部转移（`moves`）由定义与当前状态自动推导。
- **原语隐式打印判定**：“repl 的核心是运行后能有正确的结果可以知道”、“不应该是限定在最后一行才被显示”、“回显为什么不是隐式调用 print”。
- **复用宿主 `eval` 混用外部工具**：“不单独做工具最大的意义是，为什么要程序化编排，是为了把外部的信息直接拿进来当作状态注册，而不需要 ai 再抄一遍，而且中途可以自由混合比如 gh 这种东西”。

## 三、已证伪并淘汰的替代方案（防止后续重走弯路）

在会话 `01a1db88` 的设计阶段，以下 5 种方案经过 `eval` 内核实测探针被证伪淘汰：

| 淘汰方案 | 淘汰原因与实测依据 |
|---|---|
| **1. 底层引入 `Effect` (`effect/workflow`) 或 `XState`** | ① **内核无法按包名 import**：在 OMP `eval` 内核中实测 `import("effect")`、`import("typescript")` 等 5 个包全部报找不到模块（内核仅支持内置 `node:*` 和绝对文件路径）；② Effect 的内存引擎在替换定义后状态即丢失，仍需自己实现约 10 个方法的持久化引擎、定义指纹比对和 `retract`，得不偿失。 |
| **2. 闭包式 String Diagram DSL (`diagram("name", d => { ... })`)** | 闭包要求一次性写完并整体求值：改一条线或一个盒子必须重跑整个闭包；闭包内的占位符在 REPL 中无法单独求值查看；不符合一步步探索、随时反悔的 REPL 工作流。 |
| **3. Proxy 属性赋值拦截 (`f.work = {...}`, `f.scout.plan`)** | 在内核中实测了 12 种 REPL 操作发现是典型反模式：① 一个对象身兼“定义”和“引用”两职，`print(f.work)` 打印出 `[Function]` 而非定义内容；② `{ ...f.work, brief: "v2" }` 展开复制会丢光字段；③ 修改子属性 `f.work.agent = ...` 无法触发拦截；④ 赋值语句无法 `await` 桥接调用的合法性校验结果。 |
| **4. 用 `tool_call` 钩子做 Babel AST 改写实现逐行回显** | 宿主的 `tool_call` 钩子返回的替换后 `input` 会直接成为会话展示和持久化的记录（`src/extensibility/shared-events.ts`），导致模型后续在上下文里读到被注入了回显包装的脏代码。改为由 `flow.*` 原语内部隐式调用 `print(verdict)` 即可零侵入解决。 |
| **5. 单独注册一个新 `eval` REPL 工具** | 独立工具有独立的内核上下文，无法与宿主原本的 `eval` 共享变量，破坏了“在同一个 JS cell 里跑 `sh\`gh ...\`` 拿数据并直接 `flow.supply()` 塞进状态机”的核心优势。 |
